# AI 长期主线页面与推荐准确性数据评估

日期：2026-06-16

状态：产品与数据能力分析文档，暂不改生产逻辑。

## 零、2026-06-16 评审修订结论

本次评审后，本文档不再把“页面重构”作为第一问题。真正的第一问题是：

```text
长期名单的真理来源是谁？
```

如果长期名单仍从每日 `recommendation_picks` 自动推导，它就不是长期名单；如果第一版名单由人直接手填，却没有标注“人工 thesis”，它也会把主观判断包装成系统结论。

因此本文档修订为：

1. 先做候选草稿，再人工确认第一版长期名单。
2. 评级轴从“是否实时准确”改为“对长期判断的证据力”。
3. 平台线初版必须诚实标注为“人工 thesis + 部分数据支持”，不能伪装成已自动验证。
4. 长期主线必须有前向验证机制，不能只保存快照。
5. 名单稳定性、反证字段、版本快照必须进入验收。
6. 反证覆盖不得写成“自动覆盖”。当前瓶颈信号是结构化清单 + 自动提醒/草稿 + 人工确认，不是机器自动判定。
7. 前向验证必须拆开“主题 beta”和“选股 alpha”，主基准使用入选当日同一可交易 universe 的等权篮子。
8. 前向收益口径必须写死，避免复用盘中 entry price 造成的虚高问题。
9. 平台线的财务代理指标不等于 AI 归因验证，页面不得把 `financial_proxy_verified` 说成 `ai_attribution_verified`。

## 一、结论

`AI 主题雷达` 不应推倒重写。正确方向是在现有证据底座上新增一个“未来 1-2 年 AI 主线稳定层”。

当前系统已经有较好的证据底座：

- AI 价值链分类：`chain_metadata` / `system_universe`
- 主题证据：`ai_theme_company_evidence` / `ai_theme_company_tags`
- ETF 共识：`ai_theme_etf_universe` / `ai_theme_etf_holdings`
- 推荐与短期状态：`recommendation_picks`
- 价格、估值、涨幅：`price_daily`
- 持仓集中度与持仓体检：`real_holding_review_items`
- 瓶颈信号注册表：`stock_research/core/bottleneck_signals.py`

但当前系统没有一个独立、稳定、版本化的“长期 AI 主线名单”。如果继续从每日 `recommendation_picks` 推导长期名单，名单仍然会每天变化，无法满足用户“未来 1-2 年稳定研究框架”的需求。

因此应新增稳定事实源。但这个事实源不能凭空手填，也不能从每日推荐榜直接生成。正确流程是：

```text
系统候选草稿 -> 人工确认/删除/改理由 -> 写入长期主线稳定文件 -> 每日只更新状态
```

稳定事实源建议为：

```text
data/curated/ai_long_term_thesis.json
data/curated/ai_long_term_thesis_snapshots/
```

该文件只保存长期研究框架，不写 `watchlist`，不写真实持仓，不替代 `AI 推荐`。每次复核后归档快照，避免单个 JSON 被原地覆盖后无法回看。

核心原则：

```text
名单稳定，状态动态。
长期名单由系统候选草稿 + 人工确认 + 版本化管理决定；
每日系统只更新价格、证据、过热、事件、风险和当前状态，不自动改长期成员。
```

第一版名单的来源必须写清：

| 来源类型 | 是否允许进入第一版 | 展示要求 |
| --- | --- | --- |
| 系统候选草稿 + 人工确认 | 允许 | 显示候选依据、确认人、确认时间 |
| 纯人工 thesis | 允许但需降级 | 明确标注 `manual_thesis`，不得标为系统验证 |
| 每日推荐榜自动入选 | 不允许 | 只能作为候选线索 |
| 单纯聊天口头推荐 | 不允许 | 必须落成结构化记录后再展示 |

## 二、目标页面

页面仍放在：

```text
AI 助手 -> AI 主题雷达
```

首屏从“每日 AI 推荐解释”改成：

```text
未来 1-2 年 AI 主线
  1. 卡脖子 / 瓶颈线
  2. 好公司 / 平台线
  3. 双重命中
  4. 今日状态
  5. 本周变化
  6. 证据与审计
```

旧模块不删除，只降级为证据与审计区：

| 旧模块 | 新定位 |
| --- | --- |

| ETF 共识 | 市场共识 / 拥挤度参考 |

| 研究优先级 Top | 候选草稿辅助，不是长期名单 |

## 三、稳定层与日变层

长期主线页面必须显式拆成两层。

### 1. 稳定层

稳定层由“整张名单快照”加“成员列表”组成。版本是整张名单的属性，不是每一行的属性。

顶层字段示例：

| 字段 | 说明 |
| --- | --- |
| `version` | 例如 `AI长期主线 v2026-06-16` |
| `as_of_date` | 本次名单生效日期 |
| `reviewed_by` | 人工确认人或流程 |
| `source_policy` | 第一版名单来源说明 |
| `change_summary` | 本次复核变化摘要 |
| `members` | 成员列表 |

成员字段示例：

| 字段 | 说明 |
| --- | --- |
| `symbol` | 股票代码 |
| `market` | 市场 |
| `routes` | `bottleneck` / `platform`，双重命中由系统派生 |
| `chain` | AI 环节，例如 HBM、先进制程、配电设备、云平台 |
| `thesis_1y_2y` | 未来 1-2 年长期逻辑 |
| `counter_signals` | 反证信号清单 |
| `discipline_principle` | 稳定层只写观察原则，不写每日价格指令 |
| `thesis_status` | active / watch / retired |
| `evidence_basis` | system_evidence / manual_thesis / mixed |
| `counter_signal_review_mode` | structured_quarterly_review / manual_ad_hoc |
| `counter_signal_freshness` | fresh / aging / stale / missing |
| `counter_signal_source` | self_supply / demand_valve / manual_thesis：反证来自自身供给信号、需求阀门系统信号，还是人工 |
| `risk_factor` | 主风险因子，例如 ai_capex_cycle / hbm_cycle / power_buildout |
| `last_reviewed_at` | 最近复核时间 |
| `change_reason` | 本次变化原因 |

稳定层变化频率：

- 每周复核。
- 财报、重大订单、重大政策、重大技术变化后临时复核。
- 不因每日推荐分数变化自动增删成员。

重要约束：

- `active` 成员必须有 `counter_signals`，没有反证信号不得进入核心层。
- `platform` 路线初版如果没有结构化 AI 变现数据，必须标注 `manual_thesis` 或 `mixed`。
- `bottleneck` 路线如果属于 `bottleneck_signals.py` 的 7 只信号股，只能标注 `counter_signal_review_mode=structured_quarterly_review`；这表示“结构化清单 + 自动提醒/草稿 + 人工确认”，不表示全自动反证。
- `bottleneck` 路线如果不在上述 7 只内，必须标注 `counter_signal_review_mode=manual_ad_hoc`。
- 页面显示反证数量时，必须并排显示 `counter_signal_freshness`，避免把“没有转弱”和“没人复查/已过期”混在一起。
- `retired` 成员不从历史中删除，页面在“历史变化/移出记录”展示，不进入当前主线表。

### 2. 日变层

每日构建页面时叠加：

| 数据 | 来源 |
| --- | --- |
| 今日是否进入 AI 推荐 | `recommendation_picks` |
| 现价、PE、PEG、涨幅 | `price_daily` |
| 过热 / 急涨 / 急跌红旗 | `recommendation_picks.risk_flags_json` |
| 证据状态 | `ai_theme_company_tags` |
| ETF 共识 | `ai_theme_etf_holdings` |
| 瓶颈反证 | `bottleneck_signals.py` + `data/bottleneck_signal_reviews.json` |
| 持仓集中度 | `real_holding_review_items` |
| 事件窗口 | `event_calendar_*` / premarket gate |

日变层可以每天变，但不能自动改长期名单。

日变层新增字段建议：

| 字段 | 说明 |
| --- | --- |
| `current_action_state` | research_only / observe_only / evidence_review_needed / pause_new_research |
| `price_state` | 正常 / 过热 / 急跌 / 企稳中 |
| `evidence_freshness` | fresh / aging / stale / missing |
| `today_recommendation_hit` | 今日是否命中 AI 推荐 |
| `event_window` | 财报前 / 宏观前 / 无重大事件 |

`current_action_state` 是研究状态，不是买卖指令；它不得反向写入稳定层成员，也不得使用“等回调、可买、低吸、补仓、建仓”等会被读成交易动作的词。

## 三点五、第一版名单来源与路线边界

### 1. 候选草稿来源

第一版名单不能由实现者直接拍脑袋写入。必须先生成候选草稿，再人工确认。

候选草稿可以来自：

| 候选来源 | 可进入草稿 | 可直接入正式名单 |
| --- | --- | --- |
| AI 主题证据 confirmed/candidate | 可以 | 不可以，仍需人工确认 |
| `bottleneck_signals.py` 已覆盖的 7 只信号股 | 可以 | 不可以，仍需确认长期 thesis |
| ETF 共识命中且在系统 universe 内 | 可以 | 不可以 |
| 最新 AI 推荐多次命中 | 可以 | 不可以 |
| 人工提出的公司 | 可以 | 不可以，必须补 thesis 与反证 |

正式名单入选条件：

1. 必须有 `thesis_1y_2y`。
2. 必须有 `counter_signals`。
3. 必须有 `evidence_basis`。
4. 必须有 `change_reason`。
5. 必须明确是 `system_evidence`、`manual_thesis` 还是 `mixed`。

### 2. 平台线诚实声明

“好公司 / 平台线”初版不是完整自动化结论。当前系统还没有稳定的 AI 变现质量模型，不能自动证明平台公司已经把 AI 转化为收入、利润和现金流。

因此平台线初版只能是：

```text
人工 thesis + 部分数据支持
```

页面必须明确显示：

| 字段 | 含义 |
| --- | --- |
| `platform_evidence_level=manual_thesis` | 主要靠人工判断 |
| `platform_evidence_level=mixed` | 有部分云收入、RPO、利润率或财报证据 |
| `platform_evidence_level=financial_proxy_verified` | 未来才允许使用，表示云收入、RPO、利润率、FCF 等代理变量已结构化验证 |
| `platform_evidence_level=ai_attribution_verified` | 只有公司明确披露 AI 可归因收入/利润，且系统能结构化验证时才允许使用；默认应为空置 |

平台线最容易被叙事带偏。云收入、RPO、利润率、FCF 只能说明财务代理变量变好，不能直接证明“AI 已经变成可归因收入”。在 `ai_attribution_verified` 出现前，平台线不得被包装成 AI 变现已被系统自动验证的结论。

### 3. 卡脖子线范围声明

初版若只覆盖美股和美股 ADR，页面名称必须写清：

```text
美股 / ADR 可交易 AI 长期主线
```

不能笼统叫“全球卡脖子线”。全球最硬瓶颈可能包括非美公司，例如 ASML、TSM、SK 海力士、三星等。若无法交易或无法稳定覆盖，只能显示为“非当前交易范围的全球关键节点”，不能混入美股可操作名单。

### 4. 反证复查覆盖声明

当前结构化瓶颈复查只覆盖 `bottleneck_signals.py` 的 7 只：

```text
GEV / VRT / MU / MSFT / GOOGL / AMZN / META
```

但这 7 只也不是“全自动反证”。代码里的真实机制是：

```text
AI/系统可写草稿或提醒 -> 人工确认复查记录 -> 聚合判定采信已确认记录
```

草稿不参与聚合；超过 `STALE_AFTER_DAYS` 后，旧复查会被视为过期。并且两组聚合规则不同：

| 组 | 覆盖公司 | 聚合规则 |
| --- | --- | --- |
| bottleneck | GEV / VRT / MU | 任一转弱即 caution，三只转弱才 alert |
| capex | MSFT / GOOGL / AMZN / META | 一家转弱记一笔，两家以上转弱才 alert |

因此字段命名必须避免“auto/full”：

| 字段 | 允许值 | 含义 |
| --- | --- | --- |
| `counter_signal_review_mode` | `structured_quarterly_review` | 有结构化清单、自动提醒/草稿、人工确认复查 |
| `counter_signal_review_mode` | `manual_ad_hoc` | 只有人工临时复查，没有结构化季度流程 |
| `counter_signal_freshness` | fresh / aging / stale / missing | 反证覆盖新鲜度 |

其他瓶颈公司如果进入长期主线，必须标注 `counter_signal_review_mode=manual_ad_hoc`。页面不得让用户误以为整条卡脖子线都有同等反证复查能力。

### 5. 反证作用对象：自反证 vs 需求阀门

两组信号不仅聚合规则不同，**反证的作用对象也不同**。把它们都当成“成员自己的反证”会得出方向反了的降级。

| 信号组 | 反证谁 | 成员里怎么用 |
| --- | --- | --- |
| bottleneck（GEV/VRT/MU） | 反证**自己**：供给/订单/价格转弱 = 这只自身瓶颈 thesis 走弱 | `counter_signal_source=self_supply` |
| capex（MSFT/GOOGL/AMZN/META） | 反证**整条供应链需求**（NVDA/TSM/电力/光模块/服务器），是 AI 供应链的需求总阀门，不是这 4 家自身的反证 | 供给侧成员挂 `counter_signal_source=demand_valve`，引用 capex 组聚合 |

两条硬约束：

- **capex 那 4 只若自己进名单当成员，`counter_signal_source` 不得为 `self_supply`。** 它们的 capex 信号是供应链的需求反证，不是它们自身 thesis 的反证；自身反证要么走 `manual_thesis`。
- **META 在 capex 组里方向相反**（见 `bottleneck_signals.py` 注释）：META 下调 capex 对它自己常是利好、对整条供应链是需求转弱的坏信号。demand_valve 聚合采信 META 必须用“对供应链”的方向，不能当成 META 自身利空。

### 6. 名单级集中度：整张表可能是同一笔赌注

逐只标了路线和反证还不够。**整张名单很可能押在同一个风险因子上**：卡脖子供给（GEV/VRT/MU/光模块/电力/服务器）和云平台需求，本质都赌“AI capex 周期持续”——而 capex 组就是那个总阀门，它一转，供给侧会一起崩。逐票看各有 thesis，合起来是一笔集中赌注。

因此必须有**名单级**约束，不只是逐票约束：

- 单一 `risk_factor` 成员占比超过阈值（例如 50%）时，名单必须显式标“单因子集中”，不得展示为“分散的长期主线”。
- 必须提供 **portfolio overlay**：把名单因子暴露**叠加用户真实持仓**（当前 GOOGL 高度集中）算合并暴露，回答“这张名单是分散，还是在给已有的 capex 赌注盖章”。这是真钱层最该显示的一条。

## 四、推荐不准确因素与当前数据能力

下面不再按“是否实时准确”评估。未来 1-2 年主线研究并不需要 tick 级实时数据；真正重要的是：

```text
这个数据对长期判断的证据力有多强？
能不能直接支撑入选、降级或反证？
是否必须标注口径和日期？
```

评级说明改为：

| 等级 | 含义 |
| --- | --- |
| A | 对长期判断有直接证据力，可直接展示，但仍需标日期 |
| B | 有较强公开证据，可展示，但必须标注口径、来源和日期 |
| C | 主要是文本证据或人工 thesis，只能作为观察依据 |
| D | 当前缺失，不能支撑入选或降级 |

实时性作为附属字段记录，不作为主评级。

### 1. 估值透支

| 项 | 结论 |
| --- | --- |
| 长期证据力评级 | B |
| 现有数据 | `price_daily.forward_pe`、`trailing_pe`、`peg_ratio`、`market_cap` |
| 更新频率 | 每次行情抓取后更新，通常日频 |
| 准确性问题 | yfinance / 第三方估值字段可能滞后，forward PE 依赖一致预期口径 |
| 长期证据力 | 中高。方向足够用于“估值是否透支”的提示，但不能替代 DCF |
| 页面建议 | 显示“估值压力：低/中/高 + 数据日期”，不要显示成精确合理价 |

### 2. 过热 / 拥挤交易 / 追高

| 项 | 结论 |
| --- | --- |
| 长期证据力评级 | A- |
| 现有数据 | `one_week_pct`、`one_month_pct`、`one_year_pct`、推荐红旗 `OVERHEATED_1Y`、`SHORT_TERM_RUNUP_CHASE_RISK` |
| 更新频率 | 日频，盘中局部可通过行情刷新 |
| 准确性问题 | 只能识别价格过热，不能直接识别机构拥挤程度 |
| 长期证据力 | 中。对“现在不追高”很有用，但不能否定长期 thesis |
| 页面建议 | 可直接作为“当前状态”重要输入，但措辞只能写“仅观察/暂停新增研究/不追高”，不要写成“等回调”或任何买点暗示 |

### 3. 周期顶风险

| 项 | 结论 |
| --- | --- |
| 长期证据力评级 | C |
| 现有数据 | 价格涨幅、PE、财报事件、部分财务报表、MU/VRT/GEV 瓶颈信号 |
| 更新频率 | 日频 + 财报季 |
| 准确性问题 | 周期顶需要行业价格、供需、库存、订单等数据；当前没有完整行业数据库 |
| 长期证据力 | 中低。可提示风险，不能单独判定周期顶部 |
| 页面建议 | 对 MU、VRT、HPE、DELL、服务器链标为“周期敏感”，反证依赖财报和订单 |

### 4. 大厂 CapEx 反转

| 项 | 结论 |
| --- | --- |
| 长期证据力评级 | B-/C+ |
| 现有数据 | `bottleneck_signals.py` 已注册 MSFT/GOOGL/AMZN/META capex 复查清单 |
| 更新频率 | 财报季 / 人工确认 |
| 准确性问题 | 当前主要是“财报后复查清单 + 草稿确认”，不是自动抽取 capex 数字 |
| 长期证据力 | 高，但覆盖窄。它是 AI 供应链需求总阀门，需财报后确认 |
| 页面建议 | 可以展示为“需求总阀门反证”，但必须标注“财报后复核” |

### 5. 订单 / backlog / RPO 不等于收入

| 项 | 结论 |
| --- | --- |

## 四点五、前向验证机制

只保存快照不等于验证。长期主线页最大的认知风险，是它变成一个“永远能自圆其说”的叙事容器。

因此必须新增前向验证机制。

### 1. 验证对象

每个长期主线版本都要保存：

| 字段 | 说明 |
| --- | --- |
| `snapshot_id` | 本次长期主线快照 |
| `as_of_date` | 快照生成日期 |
| `confirmed_at` | 人工确认时间 |
| `effective_trade_date` | 用于前向验证的生效交易日 |
| `price_basis` | 收益计算价格口径 |
| `members` | 当时所有 active/watch 成员 |
| `routes` | 当时路线 |
| `thesis_1y_2y` | 当时 thesis |
| `counter_signals` | 当时反证 |
| `universe_snapshot_id` | 当时同一可交易 universe 快照 |
| `benchmark_set` | 对比基准 |
| `primary_test` | 预注册主判据 |

### 2. 基准

基准必须拆成两类，不能把主题 beta 当成选股 alpha。

| 基准 | 用途 |
| --- | --- |
| SPY | 普通美股市场 beta |
| QQQ | 科技成长 beta |
| SMH | 半导体/AI 硬件主题 beta |
| 同一可交易 universe 等权篮子 | 主基准，用来判断是否有选股 alpha |
| 路线内等权篮子 | 辅助基准，用来判断卡脖子/平台路线内是否选得更好 |

如果页面叫“美股/ADR 可交易 AI 长期主线”，则验证也必须按美股/ADR 口径。

`同一可交易 universe 等权篮子` 必须是 point-in-time 快照，不能用今天的 `system_universe` 回填历史。它应按入选当日的可交易范围生成，例如：

```text
system_universe AI/科技链当日快照
或当日 SMH/AI 相关 ETF 成分快照
```

`等权长期主线组合` 是被测对象本身，不是基准。它可以展示，但不能用来证明自己有效。

### 2.1 收益口径

前向收益必须统一使用 regular-session close-to-close，不能使用盘中 `entry_price`。

不要把数值化的 `entry_adj_close` 当成长期冻结事实保存。adjusted close 会在后续派息、拆股、合股等公司行动后重算历史整段序列；如果快照日保存的是旧调整基的 entry 数值，6 个月后再取新调整基的 exit，收益两端就不在同一口径上。

建议默认口径：

```text
entry_trade_date = 快照确认后的下一个完整交易日
exit_trade_date = 1/3/6/12 个月复盘日
price_basis = same_pull_adjusted_close_by_trade_date
收益计算 = 每次复盘从同一次价格序列里同时读取 entry_trade_date 和 exit_trade_date 的 adjusted close
```

如果系统改为保存 raw close，则必须同时保存并应用 corporate actions；否则不要混用 raw close 和 adjusted close。

如果未来为了及时性改用“当日收盘价”，必须满足两个条件：

1. 快照在当日美股开盘前已生成并冻结。
2. 长期名单和 universe 基准都用同一个当日收盘价。

禁止用确认后才知道的当日收盘价倒填 entry；禁止把冻结时的旧 `entry_adj_close` 数值和复盘时的新 adjusted close 序列混用。否则会重新引入系统之前已经踩过的盘中价/口径漂移/偷看未来偏差。

### 2.2 只度量冻结快照 + 活体对照

前向收益**只能度量冻结快照里的成员**，不能度量页面当前的活体名单。否则在验证窗口里，人工每 retire 一只输家、每漂移一次 thesis，都会从复核渠道把幸存者偏差重新灌进收益——口径再干净、基准再无偏也挡不住。

因此必须同时算两条曲线并排展示：

- `frozen_curve`：冻结快照成员，close-to-close，不随后续增删变化。
- `live_curve`：页面当前活体名单的同口径收益。
- 差额 `live − frozen` 本身就是**人工事后修正的幅度**：差额越大，说明这版主线越依赖事后把输家请出去才好看。

§八 的“连续多日 build 成员不变”只挡住了**无声**漂移；带 `change_reason` 的合法 retire 仍会在验证窗口里美化活体名单，双曲线就是用来量这部分的。

### 3. 复盘节奏

| 时间 | 看什么 |
| --- | --- |
| 1 个月 | 是否严重跑偏、是否发生反证 |
| 3 个月 | 路线是否仍成立，是否跑赢 QQQ/SMH |
| 6 个月 | thesis 是否兑现，移入/移出是否改善结果 |
| 12 个月 | 这版长期主线是否真的有 alpha |

### 4. 判断口径

必须预注册主判据，避免 4 个基准 × 4 个周期里挑一个最好看的格子讲故事。

建议主判据：

```text
6 个月 vs 同一可交易 universe 等权篮子：
中位数超额收益 > 0，
且去掉最佳单票后等权超额收益仍 > 0。
```

其余 SPY、QQQ、SMH、1/3/12 个月结果只作为辅助观察。

不能只看平均收益。必须同时看：

- 等权收益。
- 中位数收益。
- 对同一 universe 等权篮子的超额收益。
- 胜率。
- 最大回撤。
- 去掉最佳单票后的表现。
- 反证信号发生后是否及时降级。
- 反证覆盖新鲜度：fresh / aging / stale / missing。

这条继承系统之前“不能靠单只极端赢家撑住”的纪律。

### 5. 页面展示

长期主线页应有一个小型“前向验证”区：

```text
当前版本已运行 37 天
vs QQQ: +x%
vs SMH: +y%
vs 同宇宙等权: +b%
中位数: +z%
最大回撤: -a%
反证触发: 2 个
反证覆盖: 5 fresh / 2 stale / 3 missing
冻结快照: +c%
活体当前名单: +d%
冻结 vs 活体差额: d−c（人工事后修正幅度）
```

样本不足时必须显示“样本不足”，不能给结论。

## 五、总体判断

当前系统能比较可靠地做到：

| 能力 | 可信度 |
| --- | --- |
| 日频价格、估值、涨跌幅 | 较好 |
| 过热 / 急涨 / 急跌红旗 | 较好 |
| 推荐是否进入今日候选 | 较好 |
| 持仓集中度 | 较好 |
| 数据新鲜度 / 生产验收 | 较好 |
| 财报和宏观事件窗口 | 中等偏好 |
| 空头拥挤提示 | 可展示，但非实时 |

当前系统暂不能可靠自动支持：

| 能力 | 当前问题 |
| --- | --- |
| 大厂 capex 数字自动抽取 | 目前主要靠财报后复查清单 |
| backlog / RPO / book-to-bill 全池结构化 | 只有部分证据和瓶颈组检查 |
| 毛利率方向全池自动判断 | 有财报数据，但没有统一信号 |
| 客户集中全池识别 | 依赖 10-K + LLM，非生产常规字段 |
| 技术替代判断 | 只能人工 thesis |
| 借券费 / 实时 short squeeze | 免费源没有 |
| 平台线 AI 变现质量 | 需要新建判断口径 |

## 六、页面落地建议

长期主线页必须显示“长期证据力”，避免用户误以为所有结论都有同等证据支撑。

但不建议把 19 个风险/证据因子强行压成一个 A/B/C/D 总分。单一总分如果没有聚合规则，会从后门把主观判断放回来。

建议优先展示“证据力向量”：

| 维度 | 示例 |
| --- | --- |
| thesis 证据 | A / B / C / D |
| 财务代理 | A / B / C / D |
| 反证复查 | fresh / aging / stale / missing |
| 估值/过热 | 正常 / 偏热 / 过热 |
| 事件风险 | 无重大事件 / 财报前 / 宏观前 |

如果页面必须显示一个总等级，则使用保守聚合：

```text
总等级不得高于承重维度的最低档；
active 成员若反证复查为 stale/missing，总等级最多为 C；
平台线若只有财务代理、没有 AI 可归因披露，不得显示为 AI system verified。
```

建议每只股票显示：

| 字段 | 示例 |
| --- | --- |
| 长期路线 | 卡脖子 / 平台 / 双重命中 |
| 长期逻辑 | 人工确认 thesis |
| 当前状态 | 研究中 / 仅观察 / 证据待复核 / 暂停新增研究 |
| 长期证据力 | 证据力向量，或有规则的保守总等级 |
| 证据状态 | confirmed / candidate / stale / missing |
| 价格状态 | 正常 / 过热 / 急跌 / 企稳中 |
| 反证信号 | capex 下调、订单转弱、毛利率下滑等 |
| 反证复查 | structured_quarterly_review / manual_ad_hoc + freshness |
| 最近变化 | 新增 / 上调 / 下调 / 移出及原因 |

页面文案必须明确：

```text
本页是未来 1-2 年 AI 主线研究，不是今日买入清单。
长期名单每周或事件后复核；价格、证据和当前状态每日更新。
真正下单仍需经过 AI 推荐、AI 组合方案、买前审查和持仓风险约束。
```

## 七、分期建议

### P0a：候选草稿生成

- 从现有底座生成候选草稿，而不是直接写正式名单。
- 候选来源包括：AI 主题证据、ETF 共识、瓶颈信号注册表、近期多次推荐命中、人工补充。
- 草稿必须带候选理由、证据来源、候选路线、证据力向量。
- 草稿不得直接进入页面主表。

### P0b：人工确认第一版长期名单

- 人工确认、删除或修改候选草稿。
- 对纯人工加入的公司标注 `manual_thesis`。
- 对平台线标注 `platform_evidence_level`。
- 对瓶颈线标注 `counter_signal_review_mode` 和 `counter_signal_freshness`。
- 只在确认后写入稳定事实源。

### P1：把稳定事实源建起来

- 新增 `data/curated/ai_long_term_thesis.json`
- 新增 `data/curated/ai_long_term_thesis_snapshots/`
- MVP 第一天就必须归档冻结快照，不能等到 P5；P5 只负责成熟后的收益计算和展示。
- MVP 第一天就必须保存同一可交易 universe 快照，否则后面无法做无幸存者偏差的主基准。
- 初始范围若只覆盖美股/ADR，页面名称必须写成“美股/ADR 可交易 AI 长期主线”
- 顶层保存版本、日期、复核人、变化摘要；成员不单独保存版本
- 字段包括路线、长期逻辑、反证信号、观察原则、证据力、变化原因
- 不写 DB，不写 watchlist，不写真实持仓

### P2：日变状态叠加

- 读取长期主线名单
- join `price_daily`、`recommendation_picks`、`ai_theme_company_tags`
- 叠加过热、证据新鲜度、今日推荐命中、事件窗口
- 当前状态每日更新，但不改长期成员

### P3：页面重构

- AI 主题雷达首屏改为“未来 1-2 年 AI 主线”
- 旧模块下移到“证据与审计”
- 增加本周变化记录

### P4：复核工作流

- 系统定期生成新增、下调、移出候选草稿
- 人工确认后写入长期主线文件
- 每周/财报后复核
- 保存版本变化记录

### P5：前向验证

- 读取 P1 已保存的长期主线 point-in-time 快照。
- 读取 P1 已保存的同一可交易 universe point-in-time 快照，作为主基准。
- 保存 `entry_trade_date` 和复盘 `exit_trade_date`；每次复盘从同一次价格序列里同时读取 entry/exit 的 adjusted close，保证同一调整基。
- 预注册主判据：6 个月 vs 同一 universe 等权，中位数超额 > 0，且去掉最佳单票后仍 > 0。
- SPY、QQQ、SMH 只用于解释市场 beta / 主题 beta，不用于单独证明选股 alpha。
- 输出中位数、胜率、最大回撤、去掉最佳单票后的表现、反证覆盖新鲜度。
- 样本不足时不得给有效性结论。

实现前置依赖（不是在现有 `pick_outcomes` 上扩一扩，而是新建）：

- `pick_outcomes` 死绑 `recommendation_picks.run_id`、最长 horizon 是 20d 且未成熟（只有 1d 有样本）。静态策展名单没有 run_id，月级（1/3/6/12M）前向挂不上它，必须新建一条按 `snapshot_id` 的月级 outcome 链路。
- SMH 当前不在 `price_daily`：`scripts/pipeline/ingest_benchmark_prices.py` 只灌 SPY / QQQ / ^HSI / 000300.SS。要用 SMH 作主题 beta 基准，必须先把 SMH 加进基准灌入；并确认 SPY 历史够 12 个月回看。

### P6：增强数据

- 平台线财务代理指标：云收入、RPO、利润率、FCF；只有明确披露时才单列 AI 可归因收入/利润
- 瓶颈线结构化指标：book-to-bill、backlog、HBM 价格、capex 指引
- 客户集中度与毛利率方向自动化

## 八、验收边界

后续如果进入实现，必须满足：

- 打开 AI 主题雷达不改变 `watchlist`。
- 打开 AI 主题雷达不改变真实持仓。
- 长期主线不从每日推荐榜自动增删成员。
- 连续多日重复 build 时，长期成员集合必须不变；除非稳定事实源出现明确 `change_reason`。
- 日变状态变化不生成新长期版本。
- 每次长期成员变化必须有 `change_reason`。
- active 成员必须有非空 `counter_signals`。
- active 成员如果 `counter_signal_freshness=stale/missing`，页面必须明确显示“反证未复查/已过期”，不得显示为已验证安全。
- 平台线成员必须有 `platform_evidence_level`，不得把 `financial_proxy_verified` 包装成 `ai_attribution_verified`。
- 瓶颈线成员必须有 `counter_signal_review_mode` 和 `counter_signal_freshness`，不得暗示全自动反证。
- 每次复核必须归档快照，不能只原地覆盖当前 JSON。
- 前向验证必须使用 point-in-time universe 基准，不得用今天的 universe 回填历史。
- 前向收益必须使用统一 close-to-close 且同一调整基的口径，不得使用盘中 `entry_price`，不得混用冻结时旧 `entry_adj_close` 和复盘时新 adjusted close 序列。
- 前向验证必须预注册主判据，不能在多个周期/基准里事后挑最好看的结果。
- 前向验证样本不足时，页面必须显示“样本不足”，不能给策略有效结论。
- capex 组 4 只若进名单当成员，`counter_signal_source` 不得为 `self_supply`；META 在 demand_valve 聚合里必须按“对供应链”的方向，不得当作 META 自身利空。
- 每个成员必须标 `risk_factor`；单一 `risk_factor` 占比超阈值时，名单必须标“单因子集中”，并提供叠加真实持仓的合并因子暴露 overlay。
- 前向验证必须只度量冻结快照成员，并同时展示冻结 vs 活体名单两条曲线；差额即人工事后修正幅度。
- 页面不得暗示“长期核心 = 今天买入”。
- 涉及生产推荐或 dashboard 状态时，按 `docs/V2/产品测试验收文档.md` 运行相关验收。

## 九、最小可用版（MVP）上线边界

MVP 的目标不是“证明长期主线已经有效”，而是先让用户能稳定、可追溯、不被交易暗示误导地使用这页做研究。

MVP 上线时必须同时满足：

1. 有稳定事实源和 schema 校验。
2. 有人工确认后的第一版名单。
3. 从第一天开始冻结长期名单快照和同一 universe 快照。
4. 页面只展示研究状态，不展示买卖动作。
5. 样本未成熟前，业绩验证区只能显示“样本不足 / 未验证 alpha”。

MVP 不做：

- 不输出“可以买 / 卖出 / 补仓 / 建仓 / 低吸 / 等回调”。
- 不自动写 `watchlist`。
- 不自动写真实持仓。
- 不把证据强度 A/B/C/D 解释成“已经跑赢”。
- 不把财务代理指标解释成 AI 收入已归因验证。

### 1. 字段层反误读

交易暗示的真正载体不是标题，而是逐票状态字段和微文案。因此 MVP 必须从字段层禁用买点暗示。

允许的 `current_action_state`：

| code | 页面文案 | 含义 |
| --- | --- | --- |
| `research_only` | 研究中 | 可以继续看资料，不代表可买 |
| `observe_only` | 仅观察 | 有长期逻辑，但当前只观察 |
| `evidence_review_needed` | 证据待复核 | 证据过期、财报后未复查或关键字段缺失 |
| `pause_new_research` | 暂停新增研究 | 过热、事件窗口或反证风险较高，暂停新增研究 |

禁用词：

```text
可买 / 买入 / 卖出 / 低吸 / 补仓 / 加仓 / 建仓 / 等回调 / 目标价 / 合理价 / 到位
```

`price_state` 只能描述价格状态，例如“过热、急跌、企稳中”，不得和 `current_action_state` 组合成交易动作。

### 2. 证据强度不等于业绩验证

页面必须分成两个互不混淆的区域：

| 区域 | 回答什么 | 不回答什么 |
| --- | --- | --- |
| 证据强度 | 这只票的长期 thesis 证据强不强 | 它未来会不会跑赢 |
| 业绩验证 | 这版名单是否在前向样本里跑赢主基准 | 今天是否可以买 |

字段约束：

| 字段 | 允许含义 |
| --- | --- |
| `evidence_vector` | thesis、财务代理、反证复查、估值/过热、事件风险的证据强弱 |
| `performance_validation_status` | insufficient_sample / tracking / passed_primary_test / failed_primary_test |
| `primary_test` | 预注册主判据，不得事后修改 |

在 `performance_validation_status=insufficient_sample` 时：

- 不显示“有效 / 跑赢 / alpha 为正”。
- 只显示“样本不足，未验证 alpha”。
- 仍可显示冻结快照和活体名单开始跟踪了多少天。

在月级 outcome 链路上线前，`performance_validation_status` 只能是：

```text
insufficient_sample / tracking
```

`passed_primary_test` / `failed_primary_test` 只能由前向验证 job 根据冻结快照、同 universe 基准和预注册主判据计算产生，不允许人工直接手填。

### 3. 反证新鲜度

MVP 使用日历阈值作为基础规则，并增加事件相对规则，避免财报后没人复查却仍显示 fresh。

基础日历规则：

| 状态 | 规则 |
| --- | --- |
| `fresh` | 最近人工确认复查距今 <= 95 天 |
| `aging` | 最近人工确认复查距今 96-150 天 |
| `stale` | 最近人工确认复查距今 > 150 天 |
| `missing` | 没有人工确认复查 |

事件相对规则：

| 事件 | 处理 |
| --- | --- |
| 最新财报日期晚于 `last_reviewed_at` | 立即不得显示 `fresh` |
| 财报已发布但未复查 | `counter_signal_freshness=aging`，`freshness_reason=post_earnings_unreviewed` |
| 财报发布后超过 5 个交易日仍未复查 | `counter_signal_freshness=stale`，`freshness_reason=post_earnings_unreviewed_overdue` |
| 无法取得财报日期 | 使用日历规则，并标 `freshness_reason=calendar_only` |

优先级规则：

```text
最终 counter_signal_freshness = worst(日历规则, 事件相对规则)
严重度顺序：fresh < aging < stale < missing
事件规则只能把状态往更差方向降级，不能把 stale/missing 升成 aging/fresh。
```

页面必须显示 `freshness_reason`，不能只显示红黄绿。

### 4. MVP 数据文件与 schema

稳定事实源：

```text
data/curated/ai_long_term_thesis.json
data/curated/ai_long_term_thesis_snapshots/
data/curated/ai_long_term_universe_snapshots/
```

顶层 schema 口径：

```json
{
  "version": "AI长期主线 v2026-06-16",
  "as_of_date": "2026-06-16",
  "confirmed_at": "2026-06-16T21:30:00+08:00",
  "reviewed_by": "human",
  "source_policy": "system_draft_then_human_confirmed",
  "change_summary": "first confirmed MVP list",
  "price_basis": "same_pull_adjusted_close_by_trade_date",
  "entry_trade_date_policy": "next_regular_session_after_confirmation",
  "performance_validation_status": "insufficient_sample",
  "primary_test": {
    "horizon": "6m",
    "benchmark": "same_universe_equal_weight",
    "metric": "median_excess_return_gt_0_and_ex_best_still_gt_0"
  },
  "risk_exposure_summary": {
    "single_factor_threshold_pct": 50,
    "scope": "long_term_list_only",
    "concentration_warning": false
  },
  "members": []
}
```

稳定事实源不写真实持仓。真实持仓只进入页面动态 payload 的只读 overlay：

```json
{
  "portfolio_overlay": {
    "read_only": true,
    "as_of_date": "2026-06-16",
    "source": "real_holding_review_items",
    "combined_risk_exposure": {
      "ai_capex_cycle": 72.0
    },
    "top_overlaps": ["GOOGL"],
    "warnings": [
      "你的真实持仓与长期主线名单高度暴露于同一 AI capex 风险因子"
    ],
    "writes_real_holdings": false
  }
}
```

`risk_exposure_summary` 只回答名单内部是否单因子集中；`portfolio_overlay` 回答名单叠加真实持仓后是否加大已有赌注。两者必须都展示，不能用名单内部分散来掩盖真实持仓集中。

成员 schema 口径：

```json
{
  "symbol": "VRT",
  "market": "US",
  "routes": ["bottleneck"],
  "chain": "data_center_power_cooling",
  "thesis_status": "active",
  "thesis_1y_2y": "one to two year thesis text",
  "discipline_principle": "research only; no daily buy instruction",
  "evidence_basis": "mixed",
  "platform_evidence_level": null,
  "evidence_vector": {
    "thesis": "B",
    "financial_proxy": "B",
    "counter_signal": "fresh",
    "valuation_overheat": "normal",
    "event_risk": "none"
  },
  "counter_signals": [
    "book-to-bill drops below 1.2",
    "management pipeline turns conservative"
  ],
  "counter_signal_review_mode": "structured_quarterly_review",
  "counter_signal_freshness": "fresh",
  "freshness_reason": "review_confirmed_recently",
  "counter_signal_source": "self_supply",
  "risk_factor": "ai_capex_cycle",
  "last_reviewed_at": "2026-06-16",
  "change_reason": "first confirmed MVP list"
}
```

枚举：

| 字段 | 允许值 |
| --- | --- |
| `market` | US / ADR |
| `routes` | bottleneck / platform |
| `thesis_status` | active / watch / retired |
| `evidence_basis` | system_evidence / manual_thesis / mixed |
| `platform_evidence_level` | null / manual_thesis / mixed / financial_proxy_verified / ai_attribution_verified |
| `counter_signal_review_mode` | structured_quarterly_review / manual_ad_hoc |
| `counter_signal_freshness` | fresh / aging / stale / missing |
| `freshness_reason` | review_confirmed_recently / calendar_aging / calendar_stale / post_earnings_unreviewed / post_earnings_unreviewed_overdue / calendar_only / missing_review |
| `counter_signal_source` | self_supply / demand_valve / manual_thesis |
| `current_action_state` | research_only / observe_only / evidence_review_needed / pause_new_research |
| `performance_validation_status` | insufficient_sample / tracking / passed_primary_test / failed_primary_test |

MVP 期枚举限制：

```text
performance_validation_status 只能为 insufficient_sample / tracking；
passed_primary_test / failed_primary_test 必须等月级 outcome 链路上线后由程序写入。
```

MVP 的 universe 快照口径：

```text
US / ADR
来自 system_universe 的 AI/科技链可交易范围
排除 manual-only watchlist
保存 snapshot_id、as_of_date、symbols、source_query、excluded_reason
```

正式成员必须属于同一个 point-in-time universe 快照：

```text
members ⊆ universe_snapshot.symbols
```

如果某只股票来自人工提出、但不在 `system_universe`，只有两种合法处理：

1. 先以 `source=human_confirmed_member` 纳入本次 universe 快照，并让它同时进入同 universe 等权基准；
2. 不进入正式长期名单，只停留在候选草稿或人工研究备注。

禁止出现“分子有这只票、分母基准宇宙没有这只票”的前向验证口径。

| 测试 | 失败条件 |
| --- | --- |

| performance_not_overclaimed | 样本不足时显示跑赢、有效、alpha 为正 |
| no_watchlist_write | 打开页面或构建页面写入 `watchlist` |
| no_real_holding_write | 打开页面或构建页面写入真实持仓 |

MVP 之后再做：

- 1/3/6/12 个月收益成熟后的前向验证展示。
- SMH 等主题 beta 基准补齐。
- 月级 outcome 链路。

- book-to-bill / backlog / HBM 价格 / capex 指引自动抽取。

```text

```
